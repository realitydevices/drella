# v0

The smallest Drella that can run one coding job from start to finish. It's built by
hand; after that, Drella builds the rest of itself from `docs/`. Numbers in brackets
refer to [decisions.md](decisions.md).

> **Updated by [v0.2](v0.2.md) and [v0.3](v0.3.md):** jobs name a registered model alias
> instead of a model and endpoint, and models can need an API key (v0.2); a model can
> run Claude Code instead of OpenCode (v0.3). Where this page differs from them, the
> later page wins.

## Done when

Starting from a Linux host with no cluster, following `deploy/README.md`:

0. Install k3s, deploy Drella, and create the first token.

Then, from a laptop, with only that token:

1. Store a GitHub credential.
2. Create a job: "add a CHANGELOG.md to realitydevices/drella".
3. Follow the job's logs live.
4. The job succeeds. The agent has pushed a branch and **opened a PR itself**, and the
   job's outputs (diff, transcript) can be downloaded.

## In scope

**Cluster** (`deploy/README.md`)

A page, not a script. It covers:
- **Prerequisites:** a Linux host with a few GB of RAM and disk, and network access to
  the model endpoint.
- **Install k3s:** `curl -sfL https://get.k3s.io | sh -s - --disable traefik`. Leave out
  `--disable traefik` if nothing else on the host uses ports 80/443 and you want k3s's
  built-in ingress.
- **Kubeconfig:** copy `/etc/rancher/k3s/k3s.yaml` to your laptop and change `127.0.0.1`
  to the host's address.
- **Deploy:** `kubectl apply -k deploy/`, then create the first token.
- **Reaching Drella:** a port-forward, or one example of putting a reverse proxy in front [17].

**Deploy** (`deploy/`, kustomize)
- Namespace `drella`, containing:
  - Postgres (a single StatefulSet);
  - the `drella` Deployment and Service;
  - a ServiceAccount allowed to create Jobs and read pod logs in that namespace.
- Storage: the **local filesystem** implementation on a PVC. S3/Garage comes after v0.
- Images are built by GitHub Actions and pushed to GHCR (public): `drella` and `drella-job`.
  See **Releases** below.

**API** (`drella/`, FastAPI)

| Endpoint | What it does |
|---|---|
| `PUT /credentials/{name}` | Store a credential, encrypted with the caller's token [19] |
| `GET /credentials` | The caller's credential names (never the values) |
| `POST /jobs` | `{prompt, repo?, model}` → job id. The job is queued. `repo` is optional; a job with a repo needs a `github` credential. `model` is a registered model alias ([v0.2](v0.2.md)) |
| `PUT /models/{alias}`, `GET /models[/{alias}]`, `DELETE /models/{alias}` | Manage the models jobs can use ([v0.2](v0.2.md)) |
| `GET /jobs`, `GET /jobs/{id}` | List jobs / get status (`queued → running → succeeded / failed`) and output names |
| `GET /jobs/{id}/logs?follow=1` | Live pod logs; the archived log once the job has finished [21]. Following a queued job waits for it to start. Plain text, or server-sent events if the client accepts `text/event-stream` (ending with an `end` event carrying the final status) |
| `GET /jobs/{id}/outputs/{name}` | Download an output |
| `POST /jobs/{id}/status`, `PUT /jobs/{id}/outputs/{name}` | Used by the job itself, with its job-scoped token |
| `GET /healthz`, `GET /livez` | Readiness (the API is serving) and liveness (the queue loop is ticking). No token |

- **First token:** `drella token create --name <name>` run inside the pod
  (`kubectl exec`). It prints the token once.
- **Queue:** one queue group with concurrency 1 (`DRELLA_QUEUE_CONCURRENCY`). A loop in the API process picks the
  oldest queued job and creates the k8s Job [22].
- **Job creation:** the job's credentials are decrypted (the request carries the token)
  into a Secret owned by the Job, so Kubernetes deletes the Secret along with the Job.
  A job gets only the credentials it needs [10]: `github`, only for a job with a repo,
  and its model's API key, if the model has one ([v0.2](v0.2.md)).
- **Limits:** 1 hour timeout, 2 GB RAM [23].

**Job image** (`images/drella-job/`)
- Contains OpenCode, `git`, `gh` and the wrapper. Hermes is added after v0 [20].
- The wrapper:
  1. with a repo: clones it using the GitHub credential. Without one: starts in an
     empty working directory;
  2. checks the model endpoint answers and writes OpenCode's config, both as rendered by
     Drella for the job's model ([v0.2](v0.2.md#adapters));
  3. runs `opencode run "<prompt>"`, adding standing instructions. With a repo: *work on
     a branch, push it, open a PR with `gh`*. Without one: *write your results to `/out`*;
  4. collects `/out`: the transcript, plus the diff and PR URL for a repo job;
  5. reports the final status, then uploads `/out`. A repo job succeeds only if a PR
     exists; a job without a repo succeeds if the agent exits cleanly and wrote at least
     one output.

## Time limits and logs

A job has two time limits:
- **Soft limit (the agent's):** the wrapper runs the agent under a timer, not an
  instruction in the prompt. It stops the agent 5 minutes before the hard limit and
  reports the job failed ("the agent ran out of time"). Whatever the agent produced is
  kept.
- **Hard limit (the job's):** Kubernetes' `activeDeadlineSeconds` (1 hour) is a backstop
  for a wrapper that hangs. The wrapper's deadline is set from the same clock, so time
  spent pulling the image counts against both.

If the pod is told to stop early (deleted, evicted, node drained), the wrapper stops the
agent too. It then has the pod's grace period (2 minutes) to finish.

**What's guaranteed after the agent stops.** Everything the wrapper does next shares
the time that's left: the 5 minutes before the hard limit, or the 2-minute grace
period (less 10 seconds of margin). The agent gets at most 30 seconds to exit once
it's told to stop. Then:
1. If the job has already failed (stopped, out of time, killed), that status is
   reported straight away.
2. Outputs are collected (diff, PR lookup). Each step has its own time limit, and they
   stop 30 seconds early to leave time for the final report.
3. The final status is reported (with the PR, if there is one), then outputs are
   uploaded in order of use (PR URL, diff, transcript, the rest). Outputs that don't
   fit in the time left are lost.

So the status reaches Drella unless its API is unreachable for all of that time. Two
gaps: a step already running when the stop signal arrives (e.g. a clone, or a call to
the API) isn't cut short, so it can use up the time; and a job that never reports is
settled from Kubernetes' reason (e.g. `DeadlineExceeded`).

An agent that exits with 137 before its time is up is reported as killed (possibly out
of memory), not as out of time. Usually, though, running out of memory kills the whole
container, wrapper included, and Kubernetes reports it as `OOMKilled`.

**Logs survive the pod [21].** Kubernetes deletes a job's pod when the job times out, and
the pod's log goes with it. So Drella doesn't wait for the end: while a job runs, it
copies the pod's log to storage every 30 seconds, and once more when the job finishes.
If the pod disappears, you lose at most the last 30 seconds.

Rotation: the kubelet rotates a container's log at about 10 MB, and the log API returns
only the current file. Drella spots a rotation (the log no longer starts with what it
archived, or is shorter) and keeps the archived part as an earlier segment. The archived
log is the segments in order, with a marker where each rotation happened. At each
rotation, up to 30 seconds of output can be missing, and a job that writes more than
about 10 MB in 30 seconds loses whole segments.

## Reliability

- **The job doesn't depend on Drella being up all the time.** The job's only contact with
  Drella is the wrapper's status report and uploads at the end, and Drella restarts
  during upgrades. The wrapper retries those calls, including refused connections, for
  as long as it has time left (see above). The calls are idempotent, so retries are safe.
- **One bad job can't stall the queue.** Each job is checked on its own, errors are logged
  and the loop moves on, and every Kubernetes call has a timeout. The liveness check
  fails if the queue hasn't ticked recently, so Kubernetes restarts a stuck Drella.
- **Restarts are safe.** If Drella restarts mid-launch, it adopts the Job it already
  created rather than failing it. Secrets left behind by a failed create or launch are
  deleted.

## Security

The agent runs unattended with every tool approval skipped, and it reads content (repos,
issues) that may try to steer it. The pod is the sandbox:
- **Credentials:** only the ones the job needs (see Job creation).
- **Network:** a NetworkPolicy for job pods. No inbound traffic. Outbound is allowed only
  to DNS, the Drella API, the public internet, and the model endpoint. On private
  networks outside the cluster, only the model port (11434, Ollama's default) is
  allowed; the cluster's pod and service ranges are excluded (k3s defaults, set in the
  policy). So the agent can't reach other services on the LAN, the router or the
  cluster, except on that one port. That holds for addresses in private ranges: a node
  or router with a public address can be reached on any port through it.
- **Pod:** non-root, no privilege escalation, all capabilities dropped, the default
  seccomp profile, no service account token, and a disk limit.
- **The agent can leak what it holds.** The GitHub token and the model's API key are in
  the agent's environment,
  and the agent has internet access. A prompt-injected agent (say, from an issue or a
  file in the repo) can send them anywhere. So can code in the repo or its
  dependencies, with no prompt injection at all: tests, build scripts and package
  install hooks the agent runs inherit both in their environment. v0 doesn't prevent that; it limits the
  damage. For the model key: use one you can revoke, with a spending limit. For the
  GitHub token:
  - The token must be a fine-grained PAT for the **target repo only**, with Contents and
    Pull requests write, and **without** the Workflows permission, so it can't edit
    `.github/workflows`.
  - The target repo must protect its default branch with rules that apply to
    everyone, admins included: changes only through pull requests, **at least one
    approval** from someone other than the token's owner, and no force pushes.
    Otherwise the token can push straight to the default branch (an admin's token
    bypasses protection by default) or merge its own PR. "Never push the default
    branch" is otherwise just an instruction to the agent.
  - The repo must also protect release tags if pushing a tag triggers anything (e.g.
    a release workflow): Contents write can push tags.
  - The repo's existing CI still runs on the agent's branch, and runs code the agent
    wrote (tests, build scripts) with whatever secrets CI has.

  The job token can also be used, but only to report on and upload to that one job
  while it runs.

## Releases

Images are pinned to git tags.
- **Publishing:** pushing a tag `vX.Y.Z` publishes `drella:vX.Y.Z` and
  `drella-job:vX.Y.Z`. Pushes to `main` publish `main` and `sha-<commit>` tags, for
  testing; a `drella` image from `main` launches the `drella-job` with its `sha-<commit>`
  tag.
- **Deploying:** `deploy/` pins the `drella` image to a release tag, so a deploy needs
  that release to exist and both packages to be public on GHCR.
- **Matching job image:** the `drella` image knows its own version and launches the
  `drella-job` with the same tag, so the two always match.
- **CI permissions:** pull requests build the images but never publish, and only
  publishing runs get write access to packages.

## Out of scope

Web UI, MCP server, templates, scheduled agents, memory, agent tokens and owners,
Hermes, S3/Garage, retention, and per-agent GitHub Apps. All of these come later, built
by Drella.

## Assumptions to check

- The cluster can reach the model endpoint (e.g. Ollama on the LAN) on port 11434.
- OpenCode runs headless (`opencode run`) against an Ollama endpoint with tool calling.
- For v0 the GitHub credential is a fine-grained PAT (see Security).
