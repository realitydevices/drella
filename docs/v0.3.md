# v0.3: Claude Code as a second agent

v0.2 runs every job with OpenCode. v0.3 adds **Claude Code**, logged in with a Claude
subscription's OAuth token, as a second agent in the same job image. Which agent runs
comes from the model: a model with the `claude-code` interface runs Claude Code, and
every other model runs OpenCode. Numbers in brackets refer to
[decisions.md](decisions.md). Where this page and [v0.2](v0.2.md) differ, this page
wins.

## Done when

1. Store a Claude OAuth token (from `claude setup-token`) as a credential.
2. Register a `claude-code` model naming that credential.
3. Create a job with that model: it runs Claude Code, follows the same rules as an
   OpenCode job (time limits, stop handling, outputs, PR), and its transcript is
   readable.

## The `claude-code` interface

| Field | For a `claude-code` model |
|---|---|
| `interface` | `claude-code` |
| `base_url` | **Not used, and refused if given.** Claude Code talks to Anthropic itself |
| `model_id` | A Claude Code model name, as `claude --model` takes it: an alias such as `sonnet` or `opus`, or a full model ID. Same character rules as any `model_id` (so no `[1m]`-style suffixes) |
| `credential` | **Required:** the name of the credential holding the OAuth token. Never `github` |
| `context_length`, `max_output_tokens`, costs, `notes` | As for any model. The limits aren't passed to Claude Code; they're recorded for comparison |

Every other interface still needs a `base_url`. Jobs snapshot the model as in v0.2,
with no base URL. A credential is stripped and checked as any model key is (v0.2).

**Terms.** What Anthropic's docs say, as of v0.3 (check the pages themselves:
[authentication](https://code.claude.com/docs/en/authentication) and
[legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)):
- `claude setup-token` makes a one-year OAuth token "for CI pipelines, scripts, or other
  environments where interactive browser login isn't available". It "can only make
  model requests", and it only works with Claude Code itself (it's what
  `CLAUDE_CODE_OAUTH_TOKEN` reads).
- Plan usage limits "assume ordinary, individual usage of Claude Code and the Agent SDK".
- Developers may not "route requests through Free, Pro, Max, or Ultra plan credentials
  on behalf of their users", and "may not collect, store, or intermediate Claude.ai
  credentials or session tokens".
- Running Claude Code in a product or service for others ("hosted sandboxes or other
  agent infrastructure") needs Anthropic's Commercial Terms, and "each end user must
  authenticate with their own" API key, subscription or cloud-provider credential.

Drella's position:
- **Your own token, for your own jobs only.** You store your own subscription token,
  and only your jobs can use it: models and credentials are per token (v0.2), so no
  other caller can run on it. That's you running the unmodified Claude Code binary on
  your own subscription, from your own machine.
- **Not for hosting Drella for other people on subscriptions.** A Drella that holds
  other people's subscription tokens, or that runs jobs for others on yours, is outside
  what the subscription allows. If you host Drella for others, they use API keys (the
  `anthropic` interface, v0.2, billed to the key's owner), or you arrange the
  Commercial Terms.
- Jobs count against your plan's usage limits like any other Claude Code use.

## The agent

The adapter for the model's interface names the agent, and the runner passes it to the
pod as `DRELLA_AGENT` (`opencode` or `claude-code`). For Claude Code it also passes the
model (`DRELLA_AGENT_MODEL`). If the image doesn't know the agent, or its settings
are missing (Drella and the job image are different versions), the job fails with a
message saying so. The token reaches the pod as `DRELLA_LLM_KEY` from the
job's Secret, exactly like an API key (v0.2). The wrapper gives it to Claude Code as
`CLAUDE_CODE_OAUTH_TOKEN`, set only in the subshell that runs the agent, so it's never
on a command line.

The wrapper runs:

```
claude -p --model=<model_id> --output-format stream-json --verbose \
  --dangerously-skip-permissions --setting-sources user --strict-mcp-config "<message>"
```

- **Same job rules for both agents.** The message (the prompt plus the standing
  instructions), the soft and hard time limits, stop handling, the provisional and
  final status, redaction, the outputs and the PR check are the same as for OpenCode
  (v0.md, v0.2). The pod runs as uid 1000, which `--dangerously-skip-permissions`
  requires (Claude Code refuses it as root).
- **No preflight check.** An OAuth token can't be checked with a cheap request.
  Claude Code fails within seconds on a bad or expired token, and the job's message
  then carries Claude Code's own reason, e.g. `claude-code exited with 1: Failed to
  authenticate. API Error: 401 OAuth access token is invalid.`
- **Transcript.** Claude Code's output is a stream of JSON events. It's kept whole
  as the output `session.jsonl`, the session record, in place of OpenCode's
  `session.json`. It's redacted as it's recorded and again as it's copied, and it's
  only copied if it's still a regular file (the agent runs as the same user and could
  replace it with a symlink to `/creds/github`); the same goes for reading Claude
  Code's error from it for the job's message. The agent can still write anything it
  likes there, as it can to `/out` (v0.2's redaction gaps). The transcript (and so the live and archived log) is that
  stream turned into readable lines: the agent's text, `-> Tool {input}` for each tool
  call and `<- result` for its result (both cut to 300 characters), and a closing line
  with the number of turns and the time taken. A line that isn't JSON passes through.
- **The image.** Claude Code's native build, pinned (`CLAUDE_CODE_VERSION`) and
  checked against the SHA-256 checksums in that release's manifest. Auto-update,
  telemetry, error reporting and other non-essential traffic are off
  (`DISABLE_AUTOUPDATER`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`,
  `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`). With those off, the only host it
  contacted in testing (with an invalid token, so the session ended at the first
  request) was `api.anthropic.com`. Anthropic's docs say a setup-token "can only make
  model requests", so it can't fetch claude.ai connectors or open Remote Control.

## Security

The same attack classes as v0.2, applied to Claude Code. v0.2's Security section still
holds for both agents: the agent, and everything it runs, can read its keys.

- **The repo can't configure Claude Code.** Claude Code would otherwise load settings
  from the repo: `.claude/settings.json` and `.claude/settings.local.json` can set
  hooks (commands that run by themselves), env vars (e.g. `ANTHROPIC_BASE_URL`, to
  send the token to another server) and an `apiKeyHelper` (a command that supplies the
  key), and `.mcp.json` can start MCP servers (more commands). The wrapper passes
  `--setting-sources user` (no project or local settings) and `--strict-mcp-config`
  (no MCP servers besides ones passed on the command line, and none are). Tested with
  the real Claude Code against a repo shipping all four: without the flags, the hooks,
  the `apiKeyHelper` and the MCP server all ran and the requests went to the repo's
  server; with them, nothing ran and the only requests went to `api.anthropic.com`.
- **Hooks are off as a second layer.** The image's managed settings
  (`/etc/claude-code/managed-settings.json`, which uid 1000 can't change) set
  `disableAllHooks`. In testing that alone stops hooks but not the `apiKeyHelper`,
  env or MCP servers: the flags above are the real control.
- **CLAUDE.md.** With project settings off, Claude Code doesn't load the repo's
  `CLAUDE.md` (tested). The standing instructions already tell the agent to read
  `AGENTS.md`, `CLAUDE.md` and `CONTRIBUTING.md` itself; that content is prompt
  injection, covered in v0.md.
- **The token goes to Anthropic.** The repo can't set env vars or settings (above), and
  the pod's environment is Drella's. The token is redacted from the transcript and
  `session.jsonl` like any key, with the same gaps (v0.2).
- **The user's own settings.** Claude Code still reads user settings from its home
  directory. The image has none, and the agent can write some, but only for a later
  session, and there is none; it already holds the token anyway.
- **Network.** Nothing changes: the job NetworkPolicy already allows the public
  internet, which is where `api.anthropic.com` is.

## Out of scope

Choosing the agent independently of the model (e.g. Claude Code with an API key), MCP
servers for the agent, Hermes, and recording usage per job.

## Usage

Each job records what its agent used [46]. After the agent exits, the wrapper sums
usage from the session record it already writes (`session.json` for OpenCode,
the final `result` event in `session.jsonl` for Claude Code, parsed by the jq
programs `usage-opencode.jq` and `usage-claude-code.jq` next to the wrapper) and
sends it with the final status:

    POST /jobs/{id}/status
    {"status": "succeeded", "message": "...",
     "usage": {"input_tokens": 1000, "output_tokens": 500,
               "cache_read_tokens": 200, "cache_write_tokens": 30,
               "peak_context_tokens": 1230, "cost_usd": 0.25}}

`input_tokens` and `output_tokens` are required in `usage`; the cache counts default
to 0; `peak_context_tokens` (the largest prompt any one turn sent, input plus cache
tokens) and `cost_usd` are optional. All are non-negative; counts are integers.
OpenCode's reasoning tokens are counted as output. A missing or unparseable session
record never fails the job: the wrapper sends no usage.

Drella stores it on the job (migration 0006, nullable columns) and shows it as `usage`
in `GET /jobs/{id}` and `GET /jobs` (`null` when none was reported). Claude Code reports
its own `cost_usd`. When the agent gives none (OpenCode never does), Drella computes it
as `(input_tokens * cost_in_per_mtok + output_tokens * cost_out_per_mtok) / 1e6` from
the job's model snapshot; cache tokens aren't priced, so this under- or over-states
cached runs. With no reported cost and no prices, `cost_usd` is `null`. Compare
`peak_context_tokens` with the model's `context_length` to spot jobs that ran out of
context. A later status without `usage` (the wrapper's early failure report) keeps
usage already stored.

Usage never costs a job its status. The wrapper sends `usage` only if every number is
within the API's limits (counts: integers up to 1e13; `cost_usd`: up to 100000), and
retries the status without it if the request fails. The API drops a `usage` that fails
validation (logging a warning) and still accepts the status. A computed or reported
cost over 100000 is stored as `null`; costs are kept to 6 decimal places.

Caveats:

- Usage and cost are reported by the agent, not authoritative: a job can forge them.
- Claude Code's `total_cost_usd` is the list price (`costBasis: "list"`), not what a
  subscription actually costs.
- OpenCode's computed cost leaves out cache tokens, so it can be well under the real
  cost for cached runs.

## Fixing an existing PR

`POST /jobs` takes an optional `pr`: the number of an open pull request in `repo`
([#58](https://github.com/realitydevices/drella/issues/58)). It needs `repo` and a Drella
token whose GitHub profile can open PRs (`builder`); otherwise, or for a number below 1,
the API answers 422. It is stored on the job (migration 0007, nullable `pr`), shown as
`pr` in `GET /jobs` and `GET /jobs/{id}`, and given to the pod as `DRELLA_PR`.

With `DRELLA_PR` set, the wrapper, after cloning:

1. Looks the PR up (`gh pr view`) and fails the job, saying why, if the PR isn't `OPEN`,
   comes from a fork (cross-repository), or its head branch is the default branch or
   isn't under `drella/`. Force-pushing is only ever done to Drella's own branches.
2. Checks the branch out from origin and brings it up to date with `origin/main`:
   `git rebase`; if that conflicts, it aborts and tries `git merge --no-edit`; if that
   conflicts too, it aborts and leaves the branch as it was. The agent is then told
   about the conflict and resolves it.
3. Records the branch's remote head, and tells the agent: "You are working on PR #N,
   branch B. Commit your changes on this branch and push with
   `git push --force-with-lease origin B`. Do not open a new pull request."
4. After the agent: the job succeeds if `git ls-remote origin refs/heads/B` differs from
   the recorded head (this replaces the "opened a PR" check; otherwise it fails with
   "the agent didn't push to PR #N's branch"). The message is the PR's URL, and the
   wrapper comments "Updated by Drella job <id>." on the PR; a failed comment doesn't
   fail the job. `diff.patch` covers what the agent changed, not what the rebase or
   merge brought in. Auto-merge is not touched.

Without `pr` nothing changes.

## Operator tokens

A Drella token has a **role** ([#74](https://github.com/realitydevices/drella/issues/74),
a slice of #60): `member`, the default, or `operator`. Only the admin CLI sets it
(`drella token create --role operator`, `drella token set-role <id> <role>`; `drella
token list` shows it); no API route can. Migration 0009 adds it (existing tokens become
`member`s), with `parent_job_id`, `api_token_hash` and `api_key_wrap` on jobs.

**Member tokens:** nothing changes. Their jobs have only the job token.

**An operator token's job** gets a second, job-scoped **API token** (`dra_...`), made
when the job is created (the request holds the caller's token then) and put in the
job's Secret. The pod gets it as `DRELLA_API_TOKEN`; the wrapper redacts it like the
other secrets and tells the agent it has it. It is never the caller's own token, and
Drella stores only its hash. With it, the job may, as its caller:

| Call | |
|---|---|
| `POST /jobs` | Queue a job. The new job records `parent_job_id` (the operator job's id), shown in `GET /jobs` and `GET /jobs/{id}` (`null` otherwise). Its GitHub profile is `reader` unless the body asks for another with `profile` (see [Job profiles](#job-profiles)): never `superstar`, and never one wider than the caller's own. A child never inherits its parent's profile. At most `DRELLA_OPERATOR_MAX_CHILD_JOBS` (default 6) per run; after that, 429 with a message saying so |
| `GET /jobs`, `GET /jobs/{id}` | The caller's jobs, as the caller sees them |
| `GET /jobs/{id}/logs`, `GET /jobs/{id}/outputs/{name}` | Of the caller's jobs only. A followed log (`?follow=1`) ends, with a `[drella]` line saying why, as soon as the API token stops working (checked every 2 seconds), even if the followed job is still running |
| `GET /models`, `GET /models/{alias}` | The caller's models, so the job can choose one for the jobs it queues. Read only |

Nothing else: credentials, changing models, reporting a job's status, uploading outputs and anything an
admin does get 401. The token works only while its job is `running` and before its
deadline (`started_at` plus the job time limit), and only while its Drella token is
still an operator: a queued or finished job's token (it stops within one queue tick of the job's pod ending), or one whose token was set back to
`member`, gets 401. A job queued with an API token gets no API token of its own, so
operator jobs fan out one level only.

**Credentials.** A child job needs the caller's credentials (its model's key, a `github`
credential), which are encrypted with a key derived from the caller's token [19]. So
when the operator job is created, that derived key (not the token) is wrapped with a
key derived from the API token and stored on the job (`api_key_wrap`). A request with
the API token unwraps it to decrypt the credentials for a child, exactly as the caller's
own request would. The wrapped key is erased when the job finishes.

### Job profiles

`POST /jobs` takes an optional `profile` (`reader`, `builder` or `superstar`) from any
caller: the GitHub profile of the token Drella mints for that one job. The rule is by
permissions: every permission the asked-for profile has, the caller's Drella token's
profile must grant at the same level or higher (`write` covers `read`). So:

| Caller's profile | May ask for |
|---|---|
| `reader` | `reader` |
| `builder` | `builder`, `reader` |
| `superstar` | `superstar`, `builder`, `reader` (but not `superstar` with an operator job's API token) |

Anything else is refused with 422 saying why. Without `profile`, a job gets its Drella
token's profile, read when its token is minted; a job queued with an operator job's API
token gets `reader`. `pr` needs a profile that opens PRs (`builder`). The asked-for
profile (or a child's `reader`) is stored on the job and shown as `github_profile`;
it's `null` for jobs that use their token's profile.

**Checked again at launch.** When the queue mints the job's token (at launch, and again
on each launch retry), it reads the Drella token's profile again. A job without a
`profile` of its own gets that profile, so an admin who narrows a token narrows its
queued jobs. A job with one gets it only if the token's current profile still covers
it; otherwise the job fails ("launch failed: the job asked for the GitHub profile
'builder', which its Drella token's profile ('reader') no longer covers"). Nothing is
minted for it.

**A stored `github` credential.** Profiles limit only tokens minted from Drella's GitHub
App. If the caller has stored a `github` credential, its repo jobs use that credential
as is, so a `profile` other than the token's own can't be honoured: `POST /jobs`
refuses it with 422. Jobs queued with an API token for such a caller don't default to
`reader` either: they use the credential, and `github_profile` is `null`.

### The builder token

The supervisor queues build and fix jobs as an ordinary caller, with a separate Drella
token (typically a `builder` one), rather than as children of its own run. To give it
that token, the operator token stores it as a credential named `drella-builder`
(`PUT /credentials/drella-builder`). Each **top-level** job of an operator token then
gets its value in the job's Secret, exposed as `DRELLA_BUILDER_TOKEN`; the wrapper
redacts it like the other secrets and tells the agent it has it. Jobs queued with an
API token never get it, and neither do a member token's jobs. Jobs queued with the
builder token are that token's jobs: they aren't linked to the supervisor's run, and
the supervisor's API token can't see them (issue #82); it reads them with the builder
token.

### Security

- **An operator job can spend as its caller.** Anything its agent runs can read
  `DRELLA_API_TOKEN` and, until its pod ends, queue jobs with the caller's models,
  credentials, with a GitHub token no wider than the caller's own profile (never
  `superstar`), up to the per-run limit. A `builder` child can push branches and open PRs. Prompt injection in what the
  operator job reads can steer those jobs. Make a token an operator only for a
  supervisor you trust with that, and keep its profile and models as narrow as it needs.
- **The token is short-lived and narrow.** It can't read or change credentials or
  change models (it may list them), report a job's status, or upload outputs, and it stops working when its job's
  pod ends (within one queue tick) or reaches its deadline. A leaked API token is worth no more than the running job.
- **The database alone isn't enough.** Someone with a copy of the database and a leaked
  API token, while the job runs, can unwrap the caller's credential key and decrypt its
  credentials; neither alone can. After the job's pod ends (within one queue tick) the wrapped key is gone.
- **The builder token is long-lived.** Unlike the API token, `DRELLA_BUILDER_TOKEN` is
  a full Drella token: anything the operator job's agent runs can read it, and it keeps
  working after the job ends, until an admin revokes it, with whatever the builder
  token's profile, models and credentials allow and with no per-run limit. Prompt
  injection in what the supervisor reads can steer it. This is an accepted risk for the
  supervisor; store `drella-builder` only on an operator token you trust with it, and if
  a run may have leaked it, replace the builder token.
- **Redaction has the same gaps as for the other secrets** (v0.2): it keeps the tokens
  out of the transcript and logs, best effort.
